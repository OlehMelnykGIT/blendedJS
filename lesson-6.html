Інтернет-магазин на трьох сторінках: Home (категорії, пошук, «Load More»), Wishlist і Cart. Дані приходять з dummyjson.com через axios, списки ID товарів лежать у localStorage, код розбитий на модулі за ролями. Запуск: cd blended_products, npm run dev. Зібрана версія відкривається за посиланням. Тут код кожного модуля з поясненнями, помилки з мого варіанту з заняття і поради, які згодяться в інших проєктах.

  • Кожен модуль має одну роль: products-api тільки ходить на бекенд, render-functions тільки малює, storage тільки читає й пише localStorage. Хендлери з'єднують їх між собою, а файли сторінок (home.js, cart.js, wishlist.js) вішають слухачі.
  • У сховищі лежать тільки ID товарів, не самі товари. Ціна чи опис можуть змінитись на бекенді, а ID лишається. Тому Wishlist і Cart щоразу запитують свіжі дані за цими ID.

Запити до бекенду

Адреса бекенду, ендпоінти, розмір сторінки й ключі localStorage в одному файлі.

  • Помилка в рядку 'wishlsit' не дасть жодного повідомлення: просто «зникнуть» дані. Помилка в імені STORAGE_KEYS.wishlsit одразу видно (undefined, підказка редактора).
  • ALL_CATEGORY використовується в рендері кнопок і в перевірці кліку. Якщо колись захочеш написати «Усі», зміниш в одному місці.

Ендпоінти №2–№6 з ТЗ. Кожна функція повертає дані, а не малює їх: так ту саму функцію можна викликати з будь-якої сторінки.

  • pageParams рахує skip для всіх трьох списків. Пагінація працює і для категорій, і для пошуку: бекенд приймає limit/skip на кожному з цих ендпоінтів.
  • У params пошукове слово кодує сам axios. Рядок `?q=${query}` зламався б на символах & чи #.
  • fetchProductsByIds запускає всі запити одночасно. Три товари по 200 мс кожен приходять за ~200 мс, а не за 600, як у циклі з await всередині.
  • У моєму варіанті fetchBySearch() не мала параметра, а в URL стояла змінна category, якої в цій функції немає → ReferenceError при першому пошуку.
  • fetchByCategory і fetchBySearch не передавали limit/skip, тож бекенд повертав по 30 товарів (його значення за замовчуванням) і «Load More» для них не працював би.

Те саме без axios, щоб запустити тут. Друга сторінка категорії smartphones і три товари паралельно.

  • На другій сторінці приходить 4 товари з 16, тому «є ще сторінки?» — false: кнопка ховається.
  • Порядок у Promise.all завжди як у масиві ids, хоч би яка відповідь прийшла першою.

Сховище, посилання, рендер

Читати, записувати й перемикати ID у списках cart і wishlist.

  • getFromLS(key, defaultValue) завжди повертає щось придатне: порожній масив, якщо ключа ще немає, або якщо там лежить не JSON. Решта коду не перевіряє null.
  • toggleInList закриває обидва пункти ТЗ «додати» і «видалити» однією функцією і повертає, що сталося. Кнопка модалки після неї просто перечитує стан.
  • [...ids, id] і filter створюють новий масив, а не змінюють старий. Звичка, яка знадобиться в React: там зміна масиву «на місці» не оновлює екран.

Один об'єкт refs на всі три сторінки.

  • Сторінки різні, а refs.js один. На Wishlist немає .categories, тому refs.categoryList там null. Це нормально, поки ми не звертаємось до нього на цій сторінці.
  • Кошик рахує підсумки в [data-count] і [data-price]. Пошук за data-атрибутом не ламається, коли дизайнер перейменує класи.

Розмітка категорій, карток, товару в модалці й підсумків кошика за шаблонами з ТЗ.

  • Категорії малюються через innerHTML = (список один раз), товари — через insertAdjacentHTML('beforeend'): «Load More» дописує нові картки до вже показаних. Тому перед новим списком окремо викликаємо clearProducts().
  • data-id="${id}" на li — місток між карткою й бекендом: клік читає ID і робить запит №3.
  • images?.[0] || thumbnail: у модалці велике фото, а якщо масиву немає, маленьке. Значення за замовчуванням tags = [] рятує від undefined.map.
  • toFixed(2): 9.99 + 19.99 у JS дає 29.979999999999997, а показати треба $29.98.
  • Було Price: ${price}$ і Category:${category} без пробілу. У шаблоні ТЗ Price: $ перед числом.

Дрібні дії, які повторюються: активна кнопка, «нічого не знайдено», лоадер, лічильники, тема, скрол.

  • classList.toggle(cls, condition) замінює пару if (…) add else remove. Функції приймають true/false і самі вирішують, що робити з класом.
  • Лоадер з лічильником: на Home одночасно йдуть запит категорій і запит товарів. Без лічильника перший, що закінчився, сховав би лоадер, поки другий ще вантажиться.
  • iziToast і його CSS імпортуються тут один раз. Vite додає стилі на всі сторінки, де використано helpers.js, тож <link> на CDN у wishlist.html більше не потрібен.
  • Тема: base.css оголошує темні змінні для [data-theme='dark'] всередині :root, тобто для нащадків html. Тому атрибут ставимо на body, а не на html.
  • classList.add('not found--visible'): пробіл у назві класу. Браузер кидає InvalidCharacterError, а правильна назва — not-found--visible.
  • doActiveBtn брала глобальний event, якого в модулі немає. До того ж вона спочатку додавала клас першій кнопці, а потім одразу знімала його. Тепер setActiveCategory(button) отримує кнопку параметром: з getCategories це перша кнопка, з кліку — event.target.closest(...).

Модальне вікно

Клас modal--is-open, закриття кнопкою, бекдропом і Esc. Слухач клавіатури ставиться при відкритті й знімається при закритті.

  • removeEventListener знімає слухача, тільки якщо отримав ту саму функцію. Тому onEscPress — іменована функція, а не стрілка всередині openModal.
  • Бекдроп: слухач стоїть на .modal. Клік по вмісту спливає до нього, але тоді target — якийсь дочірній елемент. Тільки клік по самому затемненню дає target === currentTarget.
  • ID товару зберігається в refs.modal.dataset.id. Кнопки Add/Remove не знають, яку картку клікнули, тож читають його звідти.
  • body.style.overflow = 'hidden' не дає сторінці прокручуватись під відкритою модалкою.

Хендлери

«Load More» має довантажувати той список, який зараз на екрані: усі товари, категорію або пошук. Для цього хендлери тримають маленький об'єкт стану.

  • Стан описує, що показати, а requestProducts вирішує, який запит для цього потрібен. Клік по категорії, пошук і очищення пошуку тільки змінюють state і викликають showFirstPage.
  • Порядок у showFirstPage: прибрати старе (картки, «не знайдено», кнопку), показати лоадер, чекати відповідь, показати нове. finally ховає лоадер і після успіху, і після помилки.
  • return всередині try теж проходить через finally, тому порожній результат не залишає лоадер висіти.

Пункти 1, 3 і 5 ТЗ і кнопка довантаження.

  • closest('.categories__btn') замість nodeName === 'BUTTON': так перевірка не зламається, якщо в кнопку колись додадуть іконку чи <span>.
  • trim() до перевірки: рядок з пробілів стає '', і запит не йде. Так вимагає ТЗ.
  • event.currentTarget — завжди сама форма, на якій висить слухач. event.target при submit теж форма, але для інших подій це не так, тож currentTarget надійніший.
  • Якщо «Load More» впав з помилкою, state.page -= 1 повертає номер сторінки назад, і наступний клік спробує ту саму сторінку, а не пропустить її.
  • Повідомлення про кінець списку з'являється після «Load More». Коли в категорії лише 5 товарів, кнопка просто не показується, без зайвого тосту.
  • Головна помилка мого варіанту — дужки. Рядок notFoundToggle(data.products) і весь блок try { … } пошуку опинились поза функціями. Код поза функцією виконується одразу при імпорті модуля, де data і querry не існують → модуль падає, і не працює взагалі нічого. Prettier при збереженні показує такі місця: блок «з'їжджає» на нульовий відступ.
  • У пошуку return стояв після if, а не всередині. Функція завершувалась завжди, навіть із нормальним запитом.
  • iziToast використано без імпорту, а searchByQuerry не імпортовано в home.js.
  • Категорія «all» з малої, а в ТЗ «All». Тепер це одна константа ALL_CATEGORY.

Пункт 4 ТЗ, кнопки Wishlist/Cart і пошук з інших сторінок.

  • toggleModalProduct отримує ключ сховища, тому одна функція обслуговує обидві кнопки.
  • onChange?.(key) — колбек від сторінки. Home нічого не передає. Wishlist передає функцію, яка перемальовує список, коли товар прибрали з wishlist. Хендлер нічого не знає про сторінки, а сторінка сама вирішує, як реагувати.
  • Форма пошуку є в хедері кожної сторінки. На Wishlist і Cart вона переводить на Home з ?search=…, і Home одразу шукає це слово. encodeURIComponent кодує пробіли й спецсимволи для URL.
  • Кнопка «Buy» у модалці не описана в ТЗ. Тут вона кладе товар у кошик і відкриває Cart.

Сторінки

Тема, лічильники, скрол, модалка й клік по картці потрібні на кожній сторінці. Замість трьох копій — одна функція.

  • Цього файлу немає в списку ТЗ, але ТЗ дозволяє додавати файли. Без нього той самий десяток рядків стояв би в home.js, wishlist.js і cart.js.
  • { onListChange } = {}: параметр-об'єкт з деструктуризацією. initPage() без аргументів теж працює, а нові налаштування потім додаються без зміни виклику на інших сторінках.
  • Клік по картці делегується на ul.products один раз, і він працює для карток, які ще навіть не завантажені «Load More».

Точка входу головної сторінки.

  • getCategories() і getProducts() викликаються без await одна за одною, тож обидва запити йдуть паралельно.
  • URLSearchParams читає ?search=laptop з адреси. Немає параметра → null → ''.

Прочитати ID зі сховища, отримати товари через Promise.all, відрендерити.

  • Порожній wishlist — без запиту: показуємо блок «Your Wishlist Is Empty» (текст змінено в HTML сторінки).
  • key => key === STORAGE_KEYS.wishlist && renderWishlist(): додали товар у кошик — список не перемальовується; прибрали з wishlist — картка зникає одразу, навіть з відкритою модалкою.

Те саме для кошика, плюс Items, Total і кнопка Buy Products.

  • renderCartSummary([]) на початку обнуляє підсумки, тож після покупки там $0.00, а не старі цифри.
  • Після покупки кошик очищається. ТЗ вимагає тільки повідомлення, але кошик, що лишився повним після оплати, виглядав би як помилка.

Додатковий функціонал і збірка

Три пункти «Додатковий функціонал» з ТЗ.

  • Лоадер — окремий partial, як хедер і модалка: розмітка в одному файлі, а vite-plugin-html-inject вставляє її на кожну сторінку.
  • scrollUp: scroll на window додає scroll-top-btn--visible після 400px, клік робить scrollTo({ top: 0, behavior: 'smooth' }).
  • Тема зберігається під ключем theme і відновлюється в initPage на кожній сторінці. Кнопка показує ☀️/🌙. Кнопка теми стояла position: absolute поверх лічильника Wishlist, тепер вона звичайний елемент flex-хедера. Для темної теми додано кольори підсумків кошика.

Магазин викладається разом з конспектами одним Vercel-проєктом.

  • --base=/blended_products/: зібрані сторінки лежать не в корені сайту, а в папці. Без цього прапора браузер шукав би /assets/… і отримав 404 (порожня сторінка).
  • --outDir ../../_site/… рахується від root: 'src' у vite.config.js, тому два рівні вгору.
  • blended_products/index.html — заглушка для Live Server з підказкою запустити npm run dev. На Vercel її замінює зібрана сторінка.

Поради для інших проєктів

  • Розкладка за ролями (api / render / storage / handlers / refs / constants) підходить для будь-якого застосунку на чистому JS. Коли шукаєш баг, одразу знаєш файл: не той запит — products-api, не та розмітка — render-functions.
  • Функції запитів повертають дані, а не малюють. Тоді їх можна перевикористати на іншій сторінці або перенести в React без змін.
  • Шаблон async-хендлера: showLoader → try { await; render } catch { показати помилку } finally { hideLoader }. Користувач завжди бачить або результат, або повідомлення, і ніколи — вічний лоадер.
  • Стан в одному об'єкті (page, category, query). Коли додаватимеш сортування чи фільтр ціни, це ще одне поле в state і рядок у requestProducts.
  • У сховищі — ID, дані — з сервера. Так само працюють «обране», «переглянуті товари», «закладки».
  • Колбек замість перевірки сторінки. Не if (location.pathname === '/wishlist.html') всередині хендлера, а initPage({ onListChange }): спільний код не знає про конкретні сторінки.
  • Слухачі, які треба знімати (Esc у модалці, scroll для нескінченного скролу) — завжди іменовані функції.
  • Захист від «гонки» запитів. Якщо швидко клікнути дві категорії, повільніша відповідь може прийти останньою й перемалювати список не тією категорією. У великих проєктах для цього передають AbortController (axios.get(url, { signal })) і скасовують попередній запит.
  • Prettier + форматування при збереженні. Більшість помилок цього заняття — зайві чи пропущені дужки. Форматер одразу показує, де код вийшов з функції.
  • Wishlist і Cart після кожної зміни заново запитують усі товари. Для 5–10 товарів це непомітно; для великого кошика краще тримати отриманий масив і просто прибирати з нього елемент.
  • Кошик рахує кожен ID один раз. Справжньому магазину потрібна кількість: [{ id: 1, qty: 2 }] замість [1].
  • Дані з бекенду вставляються через innerHTML. dummyjson — тестовий API, але з чужими даними текст варто екранувати або створювати елементи через textContent.
